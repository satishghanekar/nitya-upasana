# Scripts

There is no build step: the browser loads these files as they are.

- `parts.js`, `splash.js` and `render.js` are plain scripts. `splash.js` sets up the splash shown until the page is ready (`#spl`: the picture for the time of day with today's star ringed; its own copy of the star centres, checked against `core/time-of-day.js` by the unit tests), or on the first opening of the day the launch animation (`#spl.launch`: the stars coming out of the night, today's growing, the day opening out of it; not for a link to a text, `?add`, a reader who asks for less motion, or a second opening that day: localStorage `nitya-launch`; a tap or a key ends it, `.skip`), and on any other opening keeps the plain splash about 1.5 s (`#spl.brief`, once a visit: sessionStorage `nitya-opened`; `features/launch.js` ends it) and puts the reader's theme on `<html>` early. `render.js` turns a piece's data into HTML (`renderPiece`, called by `core/page.js` when a piece is first opened, by `print/compose.js` and by `features/search.js`) and holds the switch to Kannada, Telugu or Gujarati letters (`SCR`), which also puts each credit's link on that language's Wikipedia page (the one `text/content.js` wrote beside it: `data-kn`, `data-te`, `data-gu`) and the site's words around a text (`data-tw`: the dhrupad's label, Previous / Next, the language, the credit's words) in that language's own words (`CONTENT.text`, from `js/strings/` `text`).
- The texts are files (`../content/texts/`). `text/load.js` fetches them as `../content/library.json` lists them (its categories, each with its texts in reading order), with `../content/timing.json` (the chanting paces, `core/timing.js`), `../content/credits.json` (who and what the texts come from) and `../content/wiki.json` (each page a link names, with its title on each Wikipedia), and `text/content.js` turns them into the pieces' data (`CONTENT`, read with `text/format.js`; each text's facts, from its own header and its category from the library, in `CONTENT.texts`), and `render.js` puts the pieces into the page. `main.js` waits for this before it starts the parts, so they find the page as if the pieces were written into it. These three are plain functions with no start-up work of their own; `text/format.js` and `text/content.js` touch no page at all, so the unit tests run them in Node.
- `text/load.js` also fetches `../content/pdfs.json` (the Library's books, `features/pdfs.js`; without it there is no Books tab), `../content/routines.json` (the four ready-made routines, `loaded.routines`) and `../content/festivals.json` (the festival rules the Vedic calendar marks), `../content/holidays.json` (its public holidays) at the same time, into `loaded`; without them the texts still load (no routine, no festivals marked).
- `store/` keeps the people on this phone and their settings and routines: `store/db.js` opens IndexedDB (database `nitya`, stores `meta` and `profiles`) with a one-second limit and one retry, falling back to memory; `store/migrate.js` upgrades settings saved by every older version and splits them into a person's part and the device's part; `store/profiles.js` is the profile model and the start-up plan (a new phone's one person, named in the menu language through `nameFirst()`, which `main.js` calls); `store/store.js` holds them while the page is open and writes them back in order (with each person's routine: `routine()` / `setRoutine()` their own, `base()` / `setBase()` the ready-made one they follow, `followed()` the one they read by); `store/backup.js` writes and reads the `.nitya` backup file (with its SHA-256). `migrate.js`, `profiles.js` and `backup.js` touch no page; all five are unit-tested in Node (with fake-indexeddb). `main.js` waits for the texts and `openStore()` together before it starts the parts.
- `main.js` is the site script. It is an ES module (`<script type="module">`), and it imports one part per topic from `core/`, `text/`, `store/` and `features/` (the `print/` files are imported by the parts that use them). `print/` holds the print layout, used by `features/print.js`.

## How the parts fit together

- Loading a part only defines its functions and variables. Each part's `init()` does its start-up work (reads the page, adds listeners), and `main.js` calls the `init()`s in a fixed order. That is the order the code ran in when it was one file (`app.js`), so a part can rely on everything above it in `main.js` being ready. Each `init()` runs on its own (`run()`): one that throws is reported in the console and the parts after it still start.
- A part imports what it uses from other parts by name, for example `import { P, save } from "../core/state.js"`. Functions can be imported in any order. A variable belongs to the part that sets it, and other parts only read it.
- A value several parts read belongs to the one part that sets it, and the others import it (an imported variable can be read, not changed): `FSA` (the default text size for this screen, "100%") in `text/autofit.js`, `rmkPop` (the open dhrupad bubble) in `text/dhrupad-markers.js`, `skCache` (the next Sankashti) in `features/sankashti.js`, and `LEAD` (the leading language, set by `apply()` through `setLead()`) in `core/state.js`.
- The settings are `P` (`core/state.js`): the person reading's settings joined with the device's. `change({ key: value }, then)` is the one way a part changes them: it puts the values into `P`, runs `then` (usually `apply()`), and saves (`save()`). `save()` writes them at once to localStorage (`aarti2-prefs`, with `pid`, the person's id: the boot copy, read first at the next start and by `render.js` before the scripts run) and, a moment later, into that person's profile in IndexedDB (`store/store.js`). Switching person replaces `P` in place (`setAll()`, then `applyPrefs()` in `features/profiles.js`). `apply()` (`features/bars.js`) turns `P` into the `data-*` switches on `<html>` that the styles react to (see `../css/README.md`).
- The layers: `core`, `text` and `store` are the ground (settings, the page, the texts, what is kept); `features` and `print` stand on them. A lower part never imports a feature or the printout: where a feature must know of something a lower part did, the lower part sends a page event and the feature listens (`nitya-fold`: a piece folded, `core/apply.js` → `features/bars.js`). `tests/site-files.spec.mjs` checks this.
- A new file must also be added to `parts.js`, so it is kept for offline use. `tests/site-files.spec.mjs` checks this.
