# How the site is built

This is for anyone changing the code. To change a text, see `README.md` instead. `js/README.md` lists every script and `css/README.md` every style file.

The site is one page, `index.html`, plus plain CSS and JavaScript files and the texts as plain-text files. **There is no build step, no framework and no server.** Cloudflare Pages serves the files exactly as they are in the repository. The JavaScript is ES modules with JSDoc types, checked by `tsc` but never compiled.

## What happens when the page opens

1. **`<head>`** loads the style files in `css/` in number order, then `js/parts.js`, the one list of the site's files. `modulepreload` links fetch the script parts in parallel.
2. **`<body>`** has the top bar, Settings, Home, the Library, the Vedic calendar, the routine builder and the dialogs, written in HTML. Help's text sits in a `<template>` and is only laid out when Help is first opened. `#pieces`, at the end of `<main>`, marks where the texts go.
3. **`js/render.js`**, a plain script, defines `renderPiece` (a text's HTML from its data) and `SCR` (Kannada letters). It also reads the boot copy of the settings and the print choices carried in a print link, before the modules run.
4. **`js/main.js`** starts the site script. `js/text/load.js` fetches `content/library.json`, the text files in `content/texts/`, `content/routines.json` and `content/festivals.json`; `js/text/content.js` turns the texts into `CONTENT` (reading each file with `js/text/format.js`). At the same time `openStore()` (`js/store/store.js`) opens IndexedDB, where the people on this phone are kept. Then each part's `init()` runs in a fixed order (listed in `js/README.md`), and `data-ready` is set on `<html>`. If the texts can't be loaded the parts start anyway, so Home, Settings and Help still work.
5. **No text is built at start-up.** A text is built the first time it is opened (`pieceEl(id)` in `js/core/page.js`, from `CONTENT` through `renderPiece`), and each part's step for a new piece (`onPiece`) runs on it then: Kannada letters, the English spelling, stanza numbers, line breaks, dhrupad markers, the fold, the highlighted line and so on. Search builds its index from `CONTENT` the first time something is searched, and print builds its own copy (see *Printing*).
6. **Until `data-ready` is set, the page is hidden**, so it never jumps while the reader's theme, languages, text size and Home's session arrive. If the script never runs, the page shows after 1.5 s anyway.
7. **After the page is shown:** the service worker (`sw.js`) saves the site for offline use, the Vedic calendar line is worked out, fonts that arrive late trigger one refit of the text size, and the print view is laid out ahead in an idle moment (`warm()` in `js/features/print.js`).

## Screens

- **Home** (`#home`, `js/features/today-card.js`): the picture and date, the Vedic calendar line (`#pan`), the festival and Sankashti lines (`#fst`, `#skt`), the Morning / Afternoon / Evening switch (`#tss`, tabs) and the session's texts (`#tsc`) and Edit (`#tsed`). `data-home` on `<html>` says Home is on screen; `data-hv` ("Home on its own", `homeView()` in `js/features/history.js`) hides the reading page under it.
- **The reading page** shows one text at a time (`.solo`) from the Library or search, with ‹ Prev / Next › in the bottom bar (`js/features/bottom-bar.js`). A title on Home starts a session: it is kept in `sessionStorage["nitya-run"]` (so it carries on after a reload), and `data-run` marks it. While it runs, every text of the session is built and shown in one scroll, in session order (`#main` as a flex column, each `.inrun` piece's CSS `order`; the page keeps the Library's order), `cur()` is the lowest piece whose top has reached the top bar, ‹ Prev / Next › stay in the session (Prev on the first and Next after the last go Home), and Print in the bottom bar (`#asp`) prints the session (`runIds()`). A jump from the Library ends it. The address follows the text (`#a5`, `#ashtak-monday`), and the reading position is kept for 12 hours.
- **Wide screens** (1024px and wider, `data-rail`): Home's column stays fixed on the left while a text, the Library or the calendar opens on the right, with the text being read marked in Home's list (`li.now`, `markNow()`).
- **Pages** over the reading page: Settings (`#panel`), the Library (`#jump`), the Vedic calendar (`#cal`) and the routine builder (`#rtb`). They open and close one way (`page()` and `PAGES` in `js/features/overlays.js`); opening one closes the open one, and `data-menu` holds the open page's id. `LAYERS` there lists every page, dialog and sheet, and says which keep Tab inside and which the phone's Back closes. A new page or dialog goes into `PAGES` / `LAYERS`.
- **Back:** every page, dialog and sheet takes a history step (`ovPush()` / `ovDone()` in `js/features/history.js`), so the phone's Back closes it; a sheet over a page gets a step of its own (`ovSub()`).
- **The bars:** the top bar (name, profile badge, Library on Home, ⋯ More, Settings) and the bottom bar (`#asc`: ‹ Prev, Home, Library, Reading, Next ›) keep fixed pixel sizes, so the text size and pinch leave them alone. On phones and tablets both tuck away while reading (`data-tuck`).

## Where the state lives

- **People.** Several people can read on one phone. Each is a profile in IndexedDB (database `nitya`, store `profiles`); store `meta` holds who is reading, the device's settings, the order of the people, when the last backup was saved and this phone's Library changes. `js/store/store.js` keeps them in memory while the page is open and writes changes back in order. If IndexedDB can't be opened within a second (tried twice; early iOS 15 can hang), everything is kept in memory for the visit and the page says so. After a backup, a restore or adding a person, the site asks the browser to keep its data (`navigator.storage.persist()`).
- **`P`** (`js/core/state.js`) holds everything the reader chose. It is the reading person's settings (`PROFILE_KEYS` in `js/store/migrate.js`: languages, menus, letters, English spelling, text size, font, dhrupad, theme, high contrast, folds, the highlighted line) joined with the device's (`DEVICE_KEYS`: keep screen on, layout, place for moonrise, the print choices).
  - `change({ key: value }, apply)` is the one way to change a setting: the values go into `P`, `apply()` brings the page up to date, then `save()` writes them.
  - `save()` writes `P` at once to `localStorage["aarti2-prefs"]` with `pid`, the person's id. This **boot copy** is read first at the next start (IndexedDB writes may not have finished when a page closes) and by `js/render.js` before the modules run. A moment later the store writes the person's profile.
  - `P.sv` is the settings version. `js/store/migrate.js` upgrades settings saved by every older version of the site, unit-tested with each shape.
  - Switching person replaces `P` in place (`setAll()`, then `applyPrefs()` in `js/features/profiles.js`), with no reload.
- **`apply()`** (`js/features/bars.js`) is the only place that turns `P` into the page: the `data-*` switches the styles react to (`data-lang` on each region; `data-ref`, `data-cols`, `data-rail`, `data-font`, `data-pref`, `data-hc` on `<html>`) and `--fs`, the text size.
- **Auto-fit** (`js/text/autofit.js`) works out the largest text size at which every verse line fits the screen on one row, measuring all lines at once in a hidden copy and remembering each result per language, font, layout and window size. It is skipped when the reader has chosen a size (`P.fsu`), and it does not count the run-on lines of the Vedic chants.
- **`checklist`** in a profile (`js/core/ticks.js`, `ticksStorage()` in `js/store/store.js`) is kept and carried by backups, but Home no longer shows or sets ticks.
- **Routines:** each profile has `routine`, in the shape of `content/routines.json` (per session `{ mode: "fixed", texts }` or `{ mode: "weekday", days: { mon: […], … } }`). `null` means the person never changed it and follows `content/routines.json`, so they get a changed default after an update; the first change in the builder copies it. The rules are pure functions in `js/core/routine.js`.
- **The Library's categories:** the built-in ones are `content/categories.json`; what the family changes on this phone (categories added, names changed, texts moved) is one object in `meta.library`, for everyone on the phone. `js/core/library.js` merges the two. The texts themselves are never changed, and the reading page's numbers follow the built-in categories.
- **Backups** (`js/store/backup.js`, `js/features/backup.js`) are `.nitya` files: plain JSON (`format: "nitya"`, `schema`, `kind: "backup"`, `app`, `created`, `payload` with every person, the device's settings and `library`, and `sha256`, a SHA-256 of the payload). Restoring checks the file (ours, not newer, checksum, cleaned values), shows who will be added, replaced or removed, and replaces everyone only after **Restore** is tapped.
- **`shared`** (`js/core/state.js`) holds the few values more than one part changes (a module can only change its own variables).
- **The styles** read only those switches and variables. `css/README.md` lists them.

## Vedic calendar and moonrise

Everything is worked out on the phone; nothing is fetched. `js/features/astronomy.js` has the sun and moon (Meeus), moonrise and the Sankashti rule. `js/core/panchang.js` gives a day's tithi, nakshatra, yoga and karana with their end times, sunrise, sunset, moonrise and the amanta month, Shaka year, samvatsara, ritu and ayana, as at that day's sunrise (Lahiri ayanamsha, the Kalnirnay / Drik convention), and a month's tithis. `js/core/festivals.js` applies the rules in `content/festivals.json` (the festival's tithi in its nija month at its part of the day: sunrise, madhyahna, aparahna, pradosh, nishita or moonrise; Makar Sankranti by the sun). They are pure functions, unit-tested against the Swiss Ephemeris and printed calendars. The place is the reader's own (Settings → Place for moonrise; the town is found in a built-in list, and only the rounded place is kept), else a city for the phone's time zone (`skLoc()` in `js/features/sankashti.js`).

## Printing

Print in the bottom bar opens the print builder (`#prm`, `js/features/print.js`). It builds a separate print view (`#pv`) for what is ticked and how, lays it out on pages, and prints that. The browser's own Print menu prints the whole Library the same way.

### The rules every printout follows

These hold for every text, so a new text prints correctly as soon as its file exists; nothing in the print code names a text.

1. **What prints comes from the text and the printout's choices, never from what the reading page shows.** Each part of a piece has a role (`parts()` in `js/features/print.js`): its title, the dhrupad at the top, a stanza, a line said once (`[dhrupad]` in a Vedic chant), a closing line (`[dhrupad bold]`), the dhrupad's ↻ marker or its repeat after a stanza, and a note of the text's own (`[note: …]`, class `nt`). The printout's dhrupad choice decides: *Once* prints the dhrupad at the top and the markers, *Every verse* prints the repeats instead (and before the first stanza when the file says `refrain-before-first`). Notes always print.
2. **Blocks.** The parts are grouped into blocks (`.pvk`), each never split between pages: a heading note (फलश्रुति) with what follows it, a marker, a repeat or a "↻ 3 times" with the stanza before it, the title and the dhrupad at the top kept with the first stanza (`data-keep`). A Vedic paragraph, or its rows side by side, may run on to the next page between two of its lines, never leaving one line alone (`data-flow`).
3. **Pages are page boxes.** `layout()` builds each printed page as a box of its own (`.pvpg`) in a page-sized copy, checks it there, and puts a forced page break before each one, the one page rule every browser follows. So Safari, Chrome and Firefox print exactly the pages planned, and the contents' page numbers are read off the boxes. A block taller than a page even at its smallest runs on between its lines (`.pvtall`) and counts for each page it takes.
4. **Layout.** In one language an aarti or ashtak is a column as wide as its longest line, centred (`.pvcol`, an explicit width), or two columns (`.pv2b` rows of `.pv2c`) when that takes fewer pages or allows a larger size. A line said once, a closing line or a note too wide for a column runs across both (it no longer stops the text from going into two columns); a stanza too wide for a column keeps the text in one. Vedic chants run as paragraphs, full width, not indented. With both languages, every line sits beside its English, one row per line pair, for aartis and Vedic chants alike (`table.pvside`; a Vedic one is `.pvprs`, its rows running on).
5. **Size.** Each text is set at one size, a zoom on its page boxes: of the fixed scale's steps its lines have room for (`LAYOUT.grow`), its own size, and smaller down to `LAYOUT.floor` (a Vedic chant to 90% only), the one with the fewest pages, then the largest, then one column (`choose()` in `js/print/pages.js`). A text set larger never takes more pages than at its own size. If laid out for real it takes more pages than planned, the next size down is tried.
6. **Numbers follow the printout.** Each category's texts are numbered 1, 2, 3… as printed (`compose()`), so texts printed from two categories read 1 | 1, 2. With both languages the number is in the original's digits, beside its title.
7. **No made-up bold.** `#pv` has `font-synthesis: none`: Safari draws a bold it has to make up as several copies of each line, which garbles the PDF's text. Traditional's bold lines are set in Noto Serif Devanagari Bold (`SC Bold`), loaded before the pages are measured.
8. **The texts are checked too.** `tests/unit/content.test.mjs` fails on a verse number that differs between the original and the English (॥ १० ॥ against `|| 1. ||`).

- **What is printed comes from the texts, not the reading page** (`js/print/compose.js`). Every piece to print is built again from `CONTENT` with `renderPiece`, and the reading page's own steps are run on that copy (Kannada letters, the English spelling, grid places, dhrupad markers, stanza numbers, line breaks, the order of the two languages). So whatever the reading page has folded, hidden or opened, the printout is the same, and a text prints the same alone as in the whole Library. `compose(ids)` builds just some texts, in reading order; one text on its own prints without the title and contents page. A print link names them (`?print=…&t=<id>,<id>`, read by `js/render.js` as `window.PRT`). `compose(ids, lang, true)` keeps the order given and numbers the texts 1, 2, 3… in it (a routine printout).
- **The builder:** **What** (`js/print/what.js`: the Library tab, with the Library's categories, a tick per text with its pages, search, Select all / Clear, a Today tab with today's sessions from `todaySessions()` in `js/features/today-card.js`, and a Routine tab), then **How** (Language, Dhrupad, Page, Print font). On a phone `data-step` shows one step at a time; from 760px both sit side by side. `openPrint({ ids, tab, from })` opens it with some texts ticked, at How: Print in the bottom bar (`#asp`), with the session being read (on the Today tab) or the text on screen. The event `nitya-print` (its detail as for `openPrint`) opens it from anywhere else (the tests use it); ⋯ More no longer has Print or Print this text. Each text starts on a new page, so a text's pages are read off the whole Library's plan, which `warm()` lays out ahead; `warm()` then lays out what is ticked, so Print prints at once.
- **Routine printouts:** the Routine tab prints a person's routine (theirs, else `content/routines.json`): the whole week or one day (today at first), with day and session chips. `js/print/select.js` (pure, unit-tested) lists each text once in routine order (Monday first, then Morning, Afternoon, Evening), gives each its tag ("Daily · Morning, Evening", "Mon, Sat, Sun · Morning"; a run of three or more days is "Mon–Fri") and lays out the week at a glance. The tab on show is what prints: `what.plan()` gives the routine's plan, which `build()` passes on. Page 1 (`routinePage()`) has the person's name and the month, the grid (days × sessions, each cell the numbers of its texts) and the contents in one column with each text's tag and page; each text's title has its tag under it (`.pvtag`, in the printout's language, the main one with both). A Library printout has neither. Open in Safari carries the person's name, routine, days and sessions in the address (`&r=`, `window.PRR`), as Safari keeps its own storage.
- **The printout's own choices** are device settings, remembered for the next printout and never applied to the reading page: `P.plang` (language: "" as the page shows it, or `mr`, `en`, `both`, read through `plang()`), `P.pref` (dhrupad), `P.por` (page) and `P.pfn` (font). The page takes the font and dhrupad as `data-font` and `data-ref` just while it prints (`pon()` / `poff()`).
- **Layouts:** one language prints in a column, on Portrait or Landscape; both languages print side by side, on Landscape only. `@page { size: landscape }` tells Chrome, Edge and Firefox; Safari keeps the sheet picked in its own dialog, so the builder tells Safari readers to pick Landscape there too. Everything is worked out from the sheet as turned (`sheet(mode)`). `FEAT_SW` in `js/core/features.js` can hide Landscape again.
- **Vedic chants** (`layout: prose`) print in one language as running paragraphs, not indented, with the verse numbers inline (`prose()`). A danda stays with the word before it and a verse number stays whole (`glue()`). Side by side, each line sits beside its English line (`table.pvside.pvprs`, two equal columns), its rows running on from page to page; `fit.js` leaves them unfitted, as their lines are sentences that wrap.
- **Fitting the lines** (`js/print/fit.js`): before the pages are planned, every printed line is measured in a page-sized frame, and each piece gets its size per language (and side by side, the columns' widths), so lines stay whole and the two columns stay in step. A line written in two lines in one language is broken in the other at its preferred break nearest the same place, and every planned wrap is written in as a `<br class="pvfb">`. `js/print/profiles.js` holds every number it works with: per script and font, the size that makes the script look as large as the others, and how far a line may shrink to fit (`LAYOUT.lineFloor`, 85%).
- **Sizes:** every line prints at 80% of its size or more, for every reason together (`LAYOUT.floor`). A piece with room to spare grows (`LAYOUT.grow`) to the largest step of a fixed scale that takes no more pages: 14, 16, 18 or 20pt for aartis and ashtaks, 15, 16 or 17pt for Vedic chants (`pvved`), English at 0.85 of those. The size is a zoom on the piece's page boxes (rule 5 above). A Vedic chant is set smaller only to 90%, where a few lines would otherwise spill onto a page.
- **Centring and two columns:** rule 4 above. The columns are balanced where a run of stanzas ends on a page (`balance()`), with a thin rule in a 10mm gap (`LAYOUT.cols.gap`).
- **Fonts:** the printout offers the same three fonts as Settings → Text font (`pfn()`: picked in the pop-up, else the text font the page is read in). **Traditional** (`data-font="classic"`, the default) prints the aartis and ashtaks in Tiro Devanagari Marathi (`SC Classic`; `SC Kn Classic`, Noto Serif Kannada, for Kannada letters) and a Vedic chant's original (`.pvved`, and `.ash.prose` on screen) in Tiro Devanagari Sanskrit; **Modern** (`std`) in Noto Sans Devanagari and Inter; **Bold** (`bold`) in Noto Serif Devanagari SemiBold (`SC Bold`). All three draw the svara marks.
- **Page planning:** rules 2 and 3 above. Each section (the contents, then each piece) is measured in a frame the size of the printed page, given its size and layout (`plan()` and `choose()` in `js/print/pages.js`, pure and unit-tested), then laid out page box by page box in that frame, each checked against the page's height as the browser lays it out; a paragraph that does not fit is split at a line end (`splitPoint()`, `splitAt()`, with the Range API, so its spans and tables are carried over whole). The finished pages are what the print view gets (`usePages()`, `data-paged` on `#pv`). The contents are laid out the same way: a line each, in two columns that read down, a category's heading kept with its first line, so no line is ever split between pages. Three things keep the frame's pages and the printed ones the same: each box is laid out and measured at its own zoom (line heights round at the zoomed size: measured unzoomed, a 40-line page came out a line short on paper); a section adds no margin, padding or rule of its own around its boxes; and every font the frame sets is asked for by name, with the characters printed, in the frame and in the page, before anything is measured (`fonts.ready` alone could resolve before a Kannada face had started to load, and every page was then measured in the fallback). The contents may also be set smaller, to the floor, where that keeps them on one page.
- **Paper:** `P.ppr` (a device setting: "" as the region suggests, `letter`, `a4`) is read through `letter()`: unless one is picked under How, Letter in the US, Canada, Mexico and the Philippines and A4 elsewhere (`LTR`). `sheet()` gives the page in mm from it, the page plan's key includes it, and `setPage` asks for that paper (`@page { size: A4 portrait }`) only when one was picked, so the printer's own paper is used otherwise. Safari keeps the paper picked in its own dialog, so the builder then says to pick the same there (`#prz`).
- **Preview:** How shows the first page of the first text ticked, in the Library's order (`first()`), as it prints (`#prsheet`). While the builder is open, `warm()` lays that one text out first, then cuts the fitted print view after its first page break (`page1()`) and keeps it in `shots` by page-plan key; `preview()` draws it in a page-sized frame with the print rules (`pcss()`, the root's attributes from `attrs()`), scaled to 120px wide. Until it is ready the sheet shows empty and faded.
- **Safari and every iPhone or iPad browser** (class `wk` on `<html>`) get the same page boxes, planned on a page 15/16 the size (Safari on a Mac prints about 16/15 larger than Chrome) and filled to 90% (Chrome's to 96%). Safari prints no page border or page-number footer (a fixed box would be drawn once down the whole printout), so on a Mac the builder suggests Chrome.
- **Printing on an iPhone:** Safari opens the print dialog only in answer to a tap, so the printout is laid out ahead and Print prints at once; otherwise the builder asks for one more tap (Ready: Print now). Printing never steps back in history (`ovDrop()`). The Home Screen app can't print at all, so Print there goes straight to Open in Safari, with the choices and the ticks in the address.
- **Slow phones:** the fitting and planning wait for the fonts for at most 2.5 s, then run with the fonts there are.
- **New scripts:** `scriptOf` in `js/print/profiles.js` works out each column's script from its letters (Devanagari, Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam or Latin), so a new script needs nothing in the print code; give it an entry in `SCRIPTS` only if `npm run print:audit` shows it looks larger or smaller than the others.
- **Tests:** `tests/unit/print-pages.test.mjs` checks the page rules (`plan`, `balance`, `choose`); `tests/print-items.spec.mjs` prints every text on its own and checks where every block and line landed and its size; `tests/print.spec.mjs` checks how printouts are put together, the builder (the Routine tab too), the contents page, routine printouts and the iPhone paths; `tests/unit/print-select.test.mjs` checks what a routine printout holds. `npm run print:audit` prints every combination a reader can choose (see `tests/README.md`).

## Offline use and updates

- `sw.js` keeps the page and every file in `js/parts.js` (styles, scripts, texts, the main fonts, the pictures and icons) in a cache named after the version.
  - The page and its parts are always fetched fresh when possible, with a 3 s limit before the saved copy is used, so the page never mixes old and new parts.
  - Everything else comes from the saved copy and is refreshed in the background. The optional fonts are saved once someone picks them.
  - If the saved copy can't be read within 2 s, the request goes to the network (Safari's storage can stall).
- **The version is written twice on purpose:** in `sw.js` (`V`) and in `<meta name="version">` in `index.html`. Browsers install a new service worker only when `sw.js` itself changes, and not every browser re-checks the files it imports, so the version must sit in `sw.js`; the page needs it at start-up too. `tests/offline.spec.mjs` fails if the two differ.
- **Check for updates** (the version line in Settings → About, `js/features/offline.js`) fetches the page and each file in `js/parts.js` fresh and reloads if any changed, so it finds changes even when the version stays the same.
- **`_headers`** lets phones keep font files for a year and pictures for a week without asking again. The page, styles and scripts are always re-checked (`no-cache`).

## Oldest supported browsers, and the fallbacks they need

The floor is **iOS 15.4** (iPhone 6s / 7, iPad Air 2 / mini 4 run up to iOS 15.8). The list is in `tests/.browserslistrc`. `npm run lint` fails on any CSS or JavaScript feature those browsers lack, unless the code checks for it first.

| Fallback | Why |
|---|---|
| `css/99-fallbacks.css` | `color-mix()` needs iOS 16.2. Without these plain colours, buttons and cards on iOS 15 lose their colours. The file must stay last. |
| `vh` before `dvh` / `svh` | Older Safari has no dynamic viewport units. |
| `setTimeout` when there is no `requestIdleCallback` | Safari has no `requestIdleCallback`, so the print warm-up just waits a moment. |
| Class `wk` on `<html>` | WebKit's print layout (see *Printing*). |
| `meta[name="version"]` read with a default | The page still runs if the tag is missing. |
| 1.5 s reveal | The page shows even if the site script fails to start, also with reduced motion. |

## What not to do

These were tried and don't work here:

- **`content-visibility: auto`** on the pieces: it changes how margins collapse, and text inside skipped content reads back empty.
- **Reordering the CSS by topic:** the cascade depends on the order rules were added (see `css/README.md`).
- **An SVG sprite for repeated icons:** compression already makes the repeats almost free, and `<use>` inside buttons behaves differently in older Safari.
- **The version only in `js/parts.js`:** see *Offline use and updates*.
- **Making `js/parts.js` or `sw.js` a module:** the service worker loads `parts.js` with `importScripts`, and module service workers are a risk on iOS 15.4.
- **Making print asynchronous** (a Worker, `requestAnimationFrame`): Safari opens the print dialog only straight from a tap.
- **Decorative fonts Martel, Amita and Yatra One:** they draw the reph wrongly (दर्शन as दरशन).

## Checking a change

- `cd tests && npm run quick` while working, and `npm run full` before a pull request is merged (see `tests/README.md`).
- `tests/MANUAL.md` is the short checklist for real phones and screen readers.
