# How the site is built

This is for anyone changing the code. To change a text, see `README.md` instead. `js/README.md` lists every script and `css/README.md` every style file.

The site is one page, `index.html`, plus plain CSS and JavaScript files and the texts as plain-text files. **There is no build step, no framework and no server.** Cloudflare Pages serves the files exactly as they are in the repository. The JavaScript is ES modules with JSDoc types, checked by `tsc` but never compiled.

## What happens when the page opens

1. **`<head>`** loads the style files in `css/` in number order, then `js/parts.js`, the one list of the site's files. `modulepreload` links fetch the script parts in parallel.
2. **The splash** (`#spl`, the first thing in `<body>`, set up by the plain script `js/splash.js`) shows from the first paint: the picture for the time of day with today's weekday star ringed, as on Home, the name, and the seven stars lighting up in turn. `js/splash.js` also puts the reader's theme from the boot copy of the settings on `<html>`, so the splash matches it. It fades out once `data-ready` is set (styles in `css/02-core.css`, "Splash"), or after 10 s if the site script never starts. `tests/unit/time-of-day.test.mjs` checks its copy of the star centres against `js/core/time-of-day.js`.
3. **`<body>`** has the top bar, Settings (with its Reading | Screen | More tabs), Home, the Library (with its Chants | Books tabs, पाठ | पोथी), the Vedic calendar, the routine builder and the dialogs, written in HTML. Help's text sits in a `<template>` and is only laid out when Help is first opened. `#pieces`, at the end of `<main>`, marks where the texts go.
4. **`js/render.js`**, a plain script, defines `renderPiece` (a text's HTML from its data) and `SCR` (Kannada letters). It also reads the boot copy of the settings and the print choices carried in a print link, before the modules run.
5. **`js/main.js`** starts the site script. `js/text/load.js` fetches `content/library.json`, the text files in `content/texts/`, `content/routines.json`, `content/festivals.json`, `content/holidays.json` and `content/pdfs.json`; `js/text/content.js` turns the texts into `CONTENT` (reading each file with `js/text/format.js`). At the same time `openStore()` (`js/store/store.js`) opens IndexedDB, where the people on this phone are kept. Then each part's `init()` runs in a fixed order (listed in `js/README.md`), each on its own, so one that fails doesn't stop the rest, and `data-ready` is set on `<html>`. If the texts can't be loaded the parts start anyway, so Home, Settings and Help still work.
6. **No text is built at start-up.** A text is built the first time it is opened (`pieceEl(id)` in `js/core/page.js`, from `CONTENT` through `renderPiece`), and each part's step for a new piece (`onPiece`) runs on it then: Kannada letters, the English spelling, stanza numbers, line breaks, dhrupad markers, the fold, the highlighted line and so on. Search builds its index from `CONTENT` the first time something is searched, and print builds its own copy (see *Printing*).
7. **Until `data-ready` is set, the page is hidden**, so it never jumps (the splash covers it meanwhile) while the reader's theme, languages, text size and Home's session arrive. If the script never runs, the page shows after 1.5 s anyway.
8. **After the page is shown:** the service worker (`sw.js`) saves the site for offline use, the Vedic calendar line is worked out, and fonts that arrive late trigger one refit of the text size.

## Screens

- **Home** (`#home`, `js/features/today-card.js`): the picture and date, the Vedic calendar line (`#pan`), the festival and Sankashti lines (`#fst`, `#skt`), the Morning / Afternoon / Evening switch (`#tss`, tabs) and the session's texts (`#tsc`) and Edit (`#tsed`). ‹ › under the date (`#tdn`) show another day (`pick.day`; `data-day` on `<html>` while it is not today): the lists, the picture's star (`setView()`), the Vedic calendar and festival lines (`homeDay()` in `js/features/vedic-calendar.js`) and the Sankashti line (`skDay()` in `js/features/sankashti.js`) follow it, the date opens the calendar at it, and `#tdb` ("Showing Wednesday", Today ›) takes This week's place. A new day, or the page shown again after 30 minutes hidden, goes back to today. `data-home` on `<html>` says Home is on screen; `data-hv` ("Home on its own", `homeView()` in `js/features/history.js`) hides the reading page under it.
- **The reading page** shows one text at a time (`.solo`) from the Library or search, with ‹ Prev / Next › in the bottom bar (`js/features/bottom-bar.js`). A title on Home starts a session: it is kept in `sessionStorage["nitya-run"]` (so it carries on after a reload, but not into another day unless it was started less than 3 hours before), and `data-run` marks it. While it runs, every text of the session is built and shown in one scroll, in session order (`#main` as a flex column, each `.inrun` piece's CSS `order`; the page keeps the Library's order), `cur()` is the lowest piece whose top has reached the top bar, or the piece just gone to while the page stays where that left it (`aimAt()` in `js/core/apply.js`: a short last text can't reach the top bar on a wide screen), ‹ Prev / Next › stay in the session (Prev on the first and Next after the last go Home), and Print in the bottom bar (`#asp`) prints the session (`runIds()`). A jump from the Library, or Home (the event `nitya-home` from `goHomeNav()`), ends it. The address follows the text (`#a5`, `#ashtak-monday`), and the reading position is kept for 12 hours.
- **Wide screens** (1024px and wider, `data-rail`): Home's column stays fixed on the left while a text, the Library or the calendar opens on the right, with the text being read marked in Home's list (`li.now`, `markNow()`).
- **The Library's books (PDFs)** (`content/pdfs.json`, written like `content/library.json`, files in `content/pdfs/`): when at least one is listed, the Library has two tabs beside Back, Chants | Books (पाठ | पोथी; `#jtb`, `js/features/contents-list.js`), and the title is for screen readers only. The Books tab sets `data-tab="pdf"` on `#jump`, and the styles show the books (`.pdfg`, at the end of `#jl`, `js/features/pdfs.js`) in place of the search box, the texts and Edit categories, under the texts' own categories (with this phone's names for them; listed again on `nitya-library` from `js/features/library.js`). Each row has a cloud before the title (online only, or saved on this phone: the page looks in the service worker's saved copies with `caches.match`, again when the reader comes back from a book) and its pages and size after it, which `npm run pdfs` (`tests/tools/pdf-info.mjs`) reads from the files into `content/pdfs.json` and a unit test checks. A book is a link that opens in a new tab, in the phone's own viewer; `sw.js` answers a `.pdf` address with the file (never the page), keeps each one once it has been opened, not before, and from then on opens it from the phone without asking the server, until the next version clears the saved copies (so a replaced PDF needs a new version).
- **Pages** over the reading page: Settings (`#panel`), the Library (`#jump`), the Vedic calendar (`#cal`) and the routine builder (`#rtb`). They open and close one way (`page()` and `PAGES` in `js/features/overlays.js`); opening one closes the open one, and `data-menu` holds the open page's id. `LAYERS` there lists every page, dialog and sheet, and says which keep Tab inside and which the phone's Back closes. A new page or dialog goes into `PAGES` / `LAYERS`.
- **Back:** every page, dialog and sheet takes a history step (`ovPush()` / `ovDone()` in `js/features/history.js`), so the phone's Back closes it; a sheet over a page gets a step of its own (`ovSub()`).
- **The bars:** the top bar (name, profile badge, Print, ⋯ More, Settings) and the bottom bar (`#asc`: ‹ Prev, Home, Library, Reading, Next ›) keep fixed pixel sizes, so the text size and pinch leave them alone. On phones and tablets both tuck away while reading (`data-tuck`), never on Home (`data-home`).

## Where the state lives

- **People.** Several people can read on one phone. Each is a profile in IndexedDB (database `nitya`, store `profiles`); store `meta` holds who is reading, the device's settings, the order of the people, when the last backup was saved and this phone's Library changes. `js/store/store.js` keeps them in memory while the page is open and writes changes back in order. If IndexedDB can't be opened within a second (tried twice; early iOS 15 can hang), everything is kept in memory for the visit and the page says so. After a backup, a restore or adding a person, the site asks the browser to keep its data (`navigator.storage.persist()`).
- **`P`** (`js/core/state.js`) holds everything the reader chose. It is the reading person's settings (`PROFILE_KEYS` in `js/store/migrate.js`: languages, menus, letters, English spelling, text size, font, dhrupad, theme, high contrast, folds, the highlighted line) joined with the device's (`DEVICE_KEYS`: keep screen on, layout, place for moonrise, the print choices).
  - `change({ key: value }, apply)` is the one way to change a setting: the values go into `P`, `apply()` brings the page up to date, then `save()` writes them.
  - `save()` writes `P` at once to `localStorage["aarti2-prefs"]` with `pid`, the person's id. This **boot copy** is read first at the next start (IndexedDB writes may not have finished when a page closes) and by `js/render.js` before the modules run. A moment later the store writes the person's profile.
  - `P.sv` is the settings version. `js/store/migrate.js` upgrades settings saved by every older version of the site, unit-tested with each shape.
  - Switching person replaces `P` in place (`setAll()`, then `applyPrefs()` in `js/features/profiles.js`), with no reload.
- **`apply()`** (`js/features/bars.js`) is the only place that turns `P` into the page: the `data-*` switches the styles react to (`data-lang` on each region; `data-ref`, `data-cols`, `data-rail`, `data-font`, `data-pref`, `data-hc` on `<html>`) and `--fs`, the text size.
- **Auto-fit** (`js/text/autofit.js`) works out the largest text size at which every verse line fits the screen on one row, measuring all lines at once in a hidden copy and remembering each result per language, font, layout and window size. It is skipped when the reader has chosen a size (`P.fsu`), and it does not count the run-on lines of the Vedic chants.
- **`checklist`** in a profile (its shape in `js/core/ticks.js`) is kept and carried by backups, but Home no longer shows or sets ticks.
- **Routines:** each profile has `routine`, in the shape of `content/routines.json` (per session `{ mode: "fixed", texts }` or `{ mode: "weekday", days: { mon: […], … } }`). `null` means the person never changed it and follows `content/routines.json`, so they get a changed default after an update; the first change in the builder copies it. The rules are pure functions in `js/core/routine.js`.
- **The Library's categories:** the built-in ones are `content/categories.json`; what the family changes on this phone (categories added, names changed, texts moved) is one object in `meta.library`, for everyone on the phone. `js/core/library.js` merges the two. The texts themselves are never changed, and the reading page's numbers follow the built-in categories.
- **Backups** (`js/store/backup.js`, `js/features/backup.js`) are `.nitya` files: plain JSON (`format: "nitya"`, `schema`, `kind: "backup"`, `app`, `created`, `payload` with every person, the device's settings and `library`, and `sha256`, a SHA-256 of the payload). Restoring checks the file (ours, not newer, checksum, cleaned values), shows who will be added, replaced or removed, and replaces everyone only after **Restore** is tapped.
- **`shared`** (`js/core/state.js`) holds the few values more than one part changes (a module can only change its own variables).
- **The styles** read only those switches and variables. `css/README.md` lists them.

## Menu languages

The menus are in Marathi or English (Settings, `P.ui`). The scripts' menu words are in a catalog, one file per language (`js/strings/en.js`, `js/strings/mr.js`), each part's words under its name; a part reads them with `menuWords("part")` (`js/core/strings.js`), and a word a language lacks is taken from English. A sentence with a value in it ("until Mon 1:21 am", "सोमवारी रात्री १:२१ पर्यंत") is a function, so each language keeps its own word order. Adding a menu language is a new file in `js/strings/` and a line in `LANGS`; `tests/unit/strings.test.mjs` checks it has every word. Not all of the site is there yet: some parts still choose between two inline words, and `index.html` writes its words as a `.mr` and an `.en` span, shown by `data-lang`. These move to the catalog part by part.

The reading languages (the texts, their titles, and the calendar's names: tithi, nakshatra, festivals) are another matter: they follow `P.lead` and `P.l2`, and Marathi can be shown in Kannada letters (`SCRIPTS` in `js/render.js`).

## Vedic calendar and moonrise

Everything is worked out on the phone; nothing is fetched. `js/features/astronomy.js` has the sun and moon (Meeus), moonrise and the Sankashti rule. `js/core/panchang.js` gives a day's tithi, nakshatra, yoga and karana with their end times, sunrise, sunset, moonrise and the amanta month, Shaka year, samvatsara, ritu and ayana, as at that day's sunrise (Lahiri ayanamsha, the Kalnirnay / Drik convention), and a month's tithis. `js/core/festivals.js` applies the rules in `content/festivals.json` (the festival's tithi in its nija month at its part of the day: sunrise, madhyahna, aparahna, pradosh, nishita or moonrise; Makar Sankranti by the sun). They are pure functions, unit-tested against the Swiss Ephemeris and printed calendars. The place is the reader's own (Settings → Place for moonrise; the town is found in a built-in list, and only the rounded place is kept), else a city for the phone's time zone (`skLoc()` in `js/features/sankashti.js`).

## Printing

Print in the top bar opens the print builder (`#prm`, `js/features/print.js`). It writes a separate print view (`#pv`) for what is ticked and how, and prints it. The browser's own Print menu prints the whole Library the same way. Nothing is measured or laid out ahead: the browser breaks the pages, by fixed rules (Satish, 2026-10-23: the page planner, the line fitting and the page numbers in the contents were taken out as too complicated).

### The rules every printout follows

These hold for every text, so a new text prints correctly as soon as its file exists; nothing in the print code names a text.

1. **What prints comes from the text and the printout's choices, never from what the reading page shows.** The texts chosen are built afresh from `CONTENT` (`js/print/compose.js`), as the reading page builds them (Kannada letters, the English spelling, stanza numbers, preferred line breaks, the order of the two languages), whatever the page has folded or hidden. Each part has a role (`parts()`): the dhrupad at the top, a stanza, a line said once, a closing line (`[dhrupad bold]`), the dhrupad's ↻ marker or its repeat after a stanza, and a note of the text's own (`[note: …]`). The printout's dhrupad choice decides: *Once* prints the dhrupad at the top and the markers, *Every verse* the repeats instead. Notes always print.
2. **Markup of its own.** The print view is written in `pv…` classes only (`write()`), so nothing of the reading page's look reaches the paper: its whole look is `css/15-print.css`, with fixed sizes.
3. **Blocks.** The parts are grouped into blocks (`.pvk`), each never split between pages: a heading note (फलश्रुति) with what follows it; a marker, a repeat or a "↻ 3 times" with the stanza before it; the dhrupad at the top with the first stanza. A Vedic paragraph (`.pvflow`), or its rows side by side, runs on from page to page between lines, never leaving one line alone (`orphans`, `widows`).
4. **Pages.** Every text, and the contents, starts on a new page; within a text the browser breaks the pages, keeping each block whole and each side-by-side row whole.
5. **Layouts.** One language, an aarti, ashtak or stotra: the stanzas in one column centred on the page, every line centred as on the reading page, none indented, so the stanzas, the dhrupad and its markers share one centre (Satish, 2026-10-23) (`.pvcol`, as wide as the stanzas' longest line); the dhrupad (at the top, with a line beside it that hugs its lines; sung again after a stanza with an empty line before it, or said once between stanzas), a bold closing line and the credit centred over the column without widening it, the credit inside the last block so it never takes a page of its own (Safari keeps nothing together otherwise); a line too long for the page wrapping with its rest indented (`.pvst`, `.pvl`). One language, a Vedic chant (`layout: prose`): running paragraphs, not indented, with room for the svara marks (`.pvpr`). Both languages: landscape, side by side, each line beside its English line, one row per line pair (`table.pvt`). Each kind has one size, English as large as the original (15pt); the text font (Modern, Traditional, Bold) is the one thing that changes how it looks, and English titles, contents and credits use the printout's English text font too, so a page has one family. The dhrupad's label is centred, and the dhrupad stands as far from the first stanza as one stanza from the next.
6. **Numbers follow the printout.** Each category's texts are numbered 1, 2, 3… as printed (`compose()`), so texts printed from two categories read 1 | 1, 2.
7. **The contents** list the texts by category (the Library's categories as this phone lists them: names the family changed, texts moved), two to a row, each row one box that never splits between pages (Safari splits grid rows), a category's heading in one box with its first row, without page numbers (a browser cannot say where its pages break). One text on its own prints without contents.
8. **No spans around spaces.** Safari prints a space beside an element's edge so narrow that two words run together: a danda is kept with its word by no-break spaces in the text (`glue()`, which also unwraps the reading page's own spans around words), and a Vedic paragraph is one text, not a span a line (tested in Safari: a span's edge at a space glues the words, a no-break space does not).
9. **No ↻ in the original language.** Safari draws ↻ from a Devanagari font as a mark that reads as ७, so a marker prints as just "ध्रुपद" (English keeps "↻ Refrain").
10. **No page frame.** Safari cannot repeat anything on every printed page, so no browser gets a frame round the page (Satish, 2026-10-23); the page margins give the same measure the frame's padding did.
11. **No made-up bold.** `#pv` has `font-synthesis: none`: Safari draws a bold it has to make up as several copies of each line, which garbles the PDF's text. Traditional's bold lines are set in Noto Serif Devanagari Bold (`SC Bold`); the printout's fonts are asked for ahead (`fontsAhead()`), as a browser prints only the faces it has loaded.
12. **The reading page matches the paper.** A Vedic chant on screen uses the same measure (33.6em, the printed page's width in its text size), the same paragraphs (no indent, a gap) and the same centred headings, so on a computer or an iPad held sideways its lines break where the printout's do (Satish, 2026-10-23). Where the screen is narrower than the page, at the automatic size, the text is scaled to fit the measure (a container query, `css/02-core.css`); once the reader picks a size (`data-fsu`) it flows instead, as it does on a phone held upright. The texts' files have no leading spaces; neither the screen nor the paper indents anything of its own.

- **The builder:** **What** (`js/print/what.js`: the Library tab, with the Library's categories, a tick per text, search, Select all / Clear; a Today tab with the sessions of the day Home shows from `shownSessions()` in `js/features/today-card.js` (named by its weekday when it is not today), a session printing in Home's order as one list headed by its day and the session (`session()`, `compose()`'s named group), with `&o=` and `&od=` (the weekday) carrying it to Safari (`window.PRO`, `window.PROD`); and a Routine tab), then **How** (Language, Dhrupad, Page, Print font). On a phone `data-step` shows one step at a time; from 760px both sit side by side. `openPrint({ ids, tab, session, day, from })` opens it with some texts ticked, at How: Print in the bottom bar (`#asp`), with the session being read (on the Today tab) or the text on screen; on Home, the session Home shows on the day it shows (`shownSession()`, `shownDay()`), even while a session is still running. The event `nitya-print` (its detail as for `openPrint`) opens it from anywhere else (the tests use it).
- **Preview:** How shows the first page of the first text ticked (`first()`), written as it prints into a page-sized frame with the print rules (`pcss()`, `attrs()`), cut at the page's foot and scaled to 120px wide.
- **Routine printouts:** the Routine tab prints a person's routine (theirs, else `content/routines.json`): the whole week or one day, with day and session chips. `js/print/select.js` (pure, unit-tested) lists each text once in routine order (Monday first, then Morning, Afternoon, Evening), gives each its tag ("Daily · Morning, Evening", "Mon–Fri · Morning") and lays out the week at a glance. Page 1 (`routinePage()`) has the person's name and the month, the grid (days × sessions, each cell the numbers of its texts) and the contents in one column with each text's tag; each text's title has its tag under it (`.pvtag`). Open in Safari carries the routine in the address (`&r=`, `window.PRR`), as Safari keeps its own storage.
- **The printout's own choices** are device settings, remembered for the next printout and never applied to the reading page: `P.plang` (language: "" as the page shows it, or `mr`, `en`, `both`, through `plang()`), `P.pref` (dhrupad), `P.por` (page), `P.pfn` (font) and `P.ppr` (paper: "" as the region suggests, `letter`, `a4`). The page takes the font and dhrupad as `data-font` and `data-ref` just while it prints (`pon()` / `poff()`). `@page { size: … }` is set for each printout (`setPage()`); Safari keeps the sheet and paper picked in its own dialog, so the builder tells Safari readers to pick them there too.
- **Printing on an iPhone:** Safari opens the print dialog only in answer to a tap. The print view is written at once, so Print prints from that tap; should a browser still ignore it, the builder asks for one more tap (Ready: Print now). The Home Screen app can't print at all, so Print there opens Safari in the same tap on iOS 17 and later (an `x-safari-https://` address, with the choices and the ticks in it) and closes the builder once the app is left; if Safari does not open, and on older iOS, it offers Open in Safari and Copy link.
- **Tests:** `tests/print.spec.mjs` prints the whole Library in each language, font and layout (Kannada letters, IAST and the dhrupad after every verse too) and checks the PDF: every text printed, listed in the contents and starting on a new page; no block split; every English line of every text on paper, read against the texts themselves (`sourceLines`); the footers; nothing screen-only. It also checks the builder, routine printouts and the iPhone paths. `tests/fonts.spec.mjs` checks the printout's fonts.

## Offline use and updates

- `sw.js` keeps the page and every file in `js/parts.js` (styles, scripts, texts, the main fonts, the pictures and icons) in a cache named after the version.
  - Every file comes from the saved copy of this version whenever it has it, at once and without asking the network, so start-up takes the same time with a weak connection or none. A file not saved yet (a first visit still saving, an optional font once picked, a PDF once opened) is fetched and then kept.
  - Nothing is downloaded again until a new version is published. Opening the site online lets the browser notice the changed `sw.js`; the new worker saves a whole fresh copy in a new cache (the font files are copied from the old one), takes over, and deletes the old copy. The page already open keeps running; the next launch opens the new version. If a file can't be fetched, that install fails and the old version stays until the next launch tries again, so the saved copy is never a mix of two versions (a first visit, with nothing to fall back on, goes on without the file and `js/features/offline.js` saves it later).
  - Requests made with `cache: 'no-store'` or `'reload'` (Check for updates, the page saving missing files) go straight to the network.
  - If the saved copy can't be read within 2 s, the request goes to the network (Safari's storage can stall).
- **The version is written twice on purpose:** in `sw.js` (`V`) and in `<meta name="version">` in `index.html`. Browsers install a new service worker only when `sw.js` itself changes, and not every browser re-checks the files it imports, so the version must sit in `sw.js`; the page needs it at start-up too. `tests/offline.spec.mjs` fails if the two differ.
- **Check for updates** (the version line in Settings → More → About, `js/features/offline.js`) fetches the page and each file in `js/parts.js` fresh. If any changed, it saves them over the saved copy and asks for the new `sw.js` (waiting until a new version is in charge, 20 s at most), then reloads, so it finds changes even when the version stays the same.
- **`_headers`** lets phones keep font files for a year and pictures for a week without asking again. The page, styles and scripts are always re-checked (`no-cache`).

## Oldest supported browsers, and the fallbacks they need

The floor is **iOS 15.4** (iPhone 6s / 7, iPad Air 2 / mini 4 run up to iOS 15.8). The list is in `tests/.browserslistrc`. `npm run lint` fails on any CSS or JavaScript feature those browsers lack, unless the code checks for it first.

| Fallback | Why |
|---|---|
| `css/99-fallbacks.css` | `color-mix()` needs iOS 16.2. Without these plain colours, buttons and cards on iOS 15 lose their colours. The file must stay last. |
| `vh` before `dvh` | Older Safari has no dynamic viewport units. |
| Class `wk` on `<html>` | WebKit's print layout (see *Printing*). |
| `meta[name="version"]` read with a default | The page still runs if the tag is missing. |
| 1.5 s reveal, 10 s splash limit | The page shows, and the splash goes, even if the site script fails to start, also with reduced motion. |

## What not to do

These were tried and don't work here:

- **`content-visibility: auto`** on the pieces: it changes how margins collapse, and text inside skipped content reads back empty.
- **Reordering the CSS by topic:** the cascade depends on the order rules were added (see `css/README.md`).
- **An SVG sprite for repeated icons:** compression already makes the repeats almost free, and `<use>` inside buttons behaves differently in older Safari.
- **The version only in `js/parts.js`:** see *Offline use and updates*.
- **Making `js/parts.js` or `sw.js` a module:** the service worker loads `parts.js` with `importScripts`, and module service workers are a risk on iOS 15.4.
- **Making print asynchronous** (a Worker, `requestAnimationFrame`): Safari opens the print dialog only straight from a tap.
- **Decorative fonts Martel, Amita and Yatra One:** they draw the reph wrongly (दर्शन as दरशन).

## Checking a change

- `cd tests && npm run quick` while working, and `npm run full` before a pull request is merged (see `tests/README.md`).
- `tests/MANUAL.md` is the short checklist for real phones and screen readers.
