# How the site is built

This is for anyone changing the code. To change a piece's text, see `README.md` instead.

The site is one page, `index.html`, plus plain CSS and JavaScript files. **There is no build step.** Cloudflare Pages serves the files exactly as they are in the repository, so an edit made on the GitHub website goes live as written.

## What happens when the page opens

1. **`<head>`** loads the 15 style files in `css/` in number order, then `js/parts.js`, the one list of the site's files. `modulepreload` links fetch the script parts in parallel.
2. **`<body>`** has the top bar, Settings, the home page and the dialogs, written in HTML. Help's text sits in a `<template>` and is only laid out when Help is first opened.
3. **At the end of `<main>`**, `#pieces` marks where the pieces go, and the plain script `js/render.js` defines `renderPieces` (the pieces' HTML) and `SCR` (Kannada letters).
4. **`js/main.js`** (`<script type="module">`) starts the site script. First `js/text/load.js` fetches `content/library.json` and the text files in `content/texts/` (and, at the same time, `content/routines.json` for the home page), `js/text/content.js` builds `CONTENT` from them (reading each file with `js/text/format.js`), and `renderPieces` puts the pieces in place of `#pieces` (rewritten in Kannada letters when chosen). At the same time `openStore()` (`js/store/store.js`) opens IndexedDB, where the people on this phone are kept (it never takes more than about two seconds: one second per try, two tries, then memory). Only then does it call each part's `init()` in a fixed order (listed in `js/README.md`), and set `data-ready` on `<html>`. So every part finds the pieces in the page, as if they had been written in the HTML. If the texts can't be loaded, the parts start anyway.
5. **Until `data-ready` is set, the page is hidden.** The reader's theme, languages and folds, the fitted text size and the home page's session list all arrive in step 4. Showing the page before that made the home page jump down by about 90px on a phone (layout shift 0.13). If the script never runs, the page shows after 1.5 s anyway.
6. **After the page is shown:**
   - The service worker (`sw.js`) saves the site for offline use.
   - Fonts that arrive late trigger one refit of the text size.
   - The print view is warmed up in an idle moment.

## Where the state lives

- **People** (version 1.4): several people can read on one phone. Each is a profile in IndexedDB (database `nitya`, store `profiles`: id, name, badge letters, colour, their settings and today's ticks); store `meta` holds who is reading, the device's settings, the order of the people and when the last backup was saved. `js/store/store.js` keeps them in memory while the page is open and writes changes back in order. If IndexedDB can't be opened (an early iOS 15 hang, an old private window) everything is kept in memory for this visit and the page says so.
- **`P`** (`js/core/state.js`) holds everything the reader chose: languages, theme, font, text size, folds, the highlighted line, and so on. It is the reading person's settings (`PROFILE_KEYS` in `js/store/migrate.js`) joined with the device's (`DEVICE_KEYS`: keep screen on, layout, location, print choices, the home card fold).
  - It is saved on the device only. Nothing is ever sent anywhere.
  - `save()` writes it at once to `localStorage["aarti2-prefs"]` with `pid`, the person's id. This **boot copy** is read first at the next start (IndexedDB writes may not have finished when a page closes), and by `js/render.js` before the scripts run. A moment later the store writes it into the person's profile.
  - `P.sv` is the settings version. `js/store/migrate.js` upgrades settings saved by every older version of the site (unit-tested with each shape in the git history). The first visit after 1.3 moves them, and the ticks, into one person called *Me*.
  - Switching person replaces `P` in place (`setAll()`, then `applyPrefs()` in `js/features/profiles.js`), with no reload.
- **`apply()`** (`js/features/bars.js`) is the only place that turns `P` into the page.
  - It sets the `data-*` switches the styles react to: `data-lang` on each region, and `data-ref`, `data-cols`, `data-rail`, `data-font`, `data-pref` and `data-hc` on `<html>`.
  - It sets `--fs`, the text size.
  - Anything that changes a setting calls `change({ key: value }, apply)` (`js/core/state.js`): the values go into `P`, `apply()` brings the page up to date, then it is saved.
- **Auto-fit** (`js/text/autofit.js`) works out the largest text size at which every verse line fits the screen on one row.
  - It measures all lines at once in a hidden copy, so the page is laid out only once.
  - It remembers each result per language, font, layout and window size.
  - It is skipped when the reader has chosen a size (`P.fsu`).
- **The home page's ticks** are kept apart from `P`, in the reading person's profile (`checklist`), for today only (`js/core/ticks.js`, given the store's storage). The old `localStorage["nitya-ticks"]` is read once, on the first visit after 1.3, and moved into the first person.
- **Each person's routine** (version 1.9, the routine builder `js/features/routine-builder.js`): in their profile (`routine`), in the shape of `content/routines.json` (per session `{ mode: "fixed", texts }` or `{ mode: "weekday", days: { mon: […], … } }`). `null` (a new person, or a profile or backup from before 1.9) means they follow `content/routines.json`; the first change in the builder copies it. Home reads the reading person's routine for today's weekday and the session (`js/features/today-card.js`). The rules for the lists are pure functions in `js/core/routine.js`, unit-tested.
- **Backups** (`js/store/backup.js`, `js/features/backup.js`) are `.nitya` files: plain JSON with every person (settings, routine, today's ticks), the device's settings and a SHA-256 of them. Restoring checks the file, shows what changes and replaces everyone only when confirmed.
- **The library's categories** (version 1.8): the built-in ones are `content/categories.json`; what the family changes on this phone (categories added, names changed, texts moved) is one object in IndexedDB `meta.library`, for everyone on the phone, and in backup files (`payload.library`; a file from 1.7 or before has none, and restoring it leaves this phone's categories as they are). `js/core/library.js` merges the two (pure, unit-tested); `js/features/library.js` shows the Library by category and the categories sheet. The texts themselves are never changed. Search (`js/text/search-core.js`, pure) finds texts by title, id, first line and category before lines.
- **The session being read** (after a title on Home is tapped) is in `sessionStorage["nitya-run"]`, so ‹ Prev and Next › keep following it if the page reloads; a jump from the Library ends it.
- **`shared`** (`js/core/state.js`) holds the seven values that more than one part changes. A JavaScript module can only change its own variables, so these live in one object everyone can write to.
- **The styles** read only those switches and variables. `css/README.md` lists them and explains the one rule for editing: a later rule for the same element wins, so change the last one.

## Printing

The Print button builds a separate print view (`#pv`, in `js/features/print.js`) for the chosen layout. Printing from the browser's own menu builds the same view.

- **What is printed comes from the texts, not the reading page** (`js/print/compose.js`, version 1.20.2). Each time the print view is built, every piece is built again from `CONTENT` as the reading page builds it (`renderPiece` in `js/render.js`), and the same start-up steps are run on that copy: Kannada letters (`SCR.el`), the English style (`englishStyle`), grid places (`gridItems`), tappable dhrupad markers (`markTappable`), stanza numbers (`numberStanzas`), preferred line breaks (`breakLines`) and the order of the two languages (`leadOrder`). The copy sits out of sight in the page while the view is built, and is removed straight after. So whatever the reading page has folded, hidden or opened (Home, one text, a session), the printout is the same: `print.spec` checks this. The printed contents follow the Library categories in `CONTENT`.
- **The print builder** (version 1.21.0, print redesign P4): Print opens `#prm` at **What** (`js/print/what.js`: the Library's categories as `shelvesNow()` in `features/library.js` lists them, a tick per text, search, Select all / Clear per category and for all), then **How** (dhrupad, page, font). On a phone `data-step` on `#prm` shows one step at a time (Next `#prnx`, back `#prbk`); from 760px both sit side by side. The bottom bar (`#prsum`) gives the texts ticked and their pages. Each text starts on a new page, so a text's pages are read off the whole Library's plan (`out.n`, and `out.toc` for the contents) that `warm()` lays out ahead anyway; the total adds the contents page when more than one text is ticked. `warm()` then lays out what is ticked (`pkey(mode, ids)`), so Print prints at once. Print sets `sel` to the ticked texts for that printout only; the browser's own menu prints the whole Library. Open in Safari carries the ticks (`&t=`), and Safari ticks them (`what.set`).
- **The printout's language** (version 1.21.3, P4c): `P.plang` (a device setting, like `pfn` and `pref`: "" as the page shows it, or `mr`, `en`, `both`) is read through `plang()` in `print.js` wherever the print code used `P.lang`: the layout (`dm`, `land`, `choice`), the page plan's key, the contents' digits, `compose(ids, lang)` (each piece's `data-lang`) and `#pv`'s `data-lang`. The reading page keeps `P.lang`. The Language row (`#prlg`) lists the main language first. The print fonts are tiles (`.prfx`, a word of the text in each font, over `.prfm`, its name); the sample line `#prfs` is gone.
- **Preview and paper** (version 1.22.1, P4d): `P.ppr` (a device setting: "" as the region suggests, `letter`, `a4`) is read through `letter()` in `print.js`; `sheet()` gives the page in mm from it, the page plan's key includes it, and `setPage` asks for that paper (`@page { size: A4 portrait }`) only when one was picked, so the printer's own paper is used otherwise. The preview (`#prsheet`) is the first page of the first text ticked, in the Library's order (`first()`): while the builder is open, `warm()` lays that one text out first (quick), then cuts the fitted print view after its first page break (`page1()`) and keeps it in `shots` by page-plan key; `preview()` draws it in a page-sized frame with the print rules (`pcss()`, the root's attributes from `attrs()`), scaled to 120px wide. Until it is ready the sheet shows empty and faded.
- **Shortcuts into the builder** (version 1.21.1, P4b): `openPrint({ ids, tab, from })` in `print.js` opens it with just those texts ticked, at How. *Print this text* (`#prt` in ⋯ More, hidden on Home by `data-home`) takes the text on screen (`cur()` in `core/apply.js`); *Print this session* (`#tspr` on Home) takes the session Home shows. What's **Today** tab lists `todaySessions()` (`features/today-card.js`: today's sessions from the reading person's routine) and All of today; a tap ticks exactly those texts (`what.set`). The bar names the text when one is ticked.
- **Some texts only** (version 1.20.5). `compose(ids)` can build just some texts (by Library id), still in reading order, and the print view then holds just those; one text on its own prints without the title and contents page. The print builder chooses them, and a print link carries them (`?print=…&t=<id>,<id>`, read in `js/render.js` as `window.PRT`, the way Open in Safari already carries the print choices). Because each piece is built and sized by itself, a text prints the same alone as in the whole Library, so the print tests check each text on its own (`tests/print-items.spec.mjs`, one tag per text).

- **Layouts:** the Print pop-up offers two choices, Portrait and Landscape. One language prints in a column on either; the original with its English prints side by side, on Landscape only (stacked, one above the other, took a third more paper and is no longer offered). A piece marked `prose` (`layout: prose` in its text file: the Atharvashirsha) prints in one language as a booklet does: running paragraphs with a first-line indent and the verse numbers inline (`prose()` in `print.js`). A paragraph starts at a stanza marked `para`, and a dhrupad stanza is a paragraph of its own (centred when it is one line, like the closing peace chant). A danda stays with the word before it and a verse number stays whole (`glue()`). Paragraphs run on from page to page. Side by side (version 1.20.8), each paragraph sits beside its English one (`.pvpair`, floats, which every browser breaks across pages): the paragraphs start level and their lines run free. `fit.js` (`pairs`) picks the original's share of the width that makes the piece shortest, writes in every line's end as laid out (`<br class="pvfb">`, planned with 2% of the column spare) so paper takes the lines the page plan counted, and draws the rule down the taller column (`.pvtl`).

- **Fitting the text** (`js/print/`): before the pages are planned, `fit.js` measures every printed line in the page-sized frame and sets each piece's size per language, and side by side the share of the width each column gets, so that lines stay whole and the two columns stay in step. Side by side, a row stays in step by line breaks too: a line written in two lines in one language is broken in the other at its preferred break nearest the same place; a row whose one side would wrap where the other fits has the other broken to match (between two words only when the first side has no better place either); and every planned wrap is written into the line as a `<br class="pvfb">`, because a line within 2% of its column may or may not wrap on paper, and a written break always does. `profiles.js` holds every number it works with: per script and text font, the size that makes the script look as large as the others, and how much smaller a line may go to fit (no more than 15% by the fitting alone, `LAYOUT.lineFloor`).
- **Sizes** (version 1.20.6, Satish 2026-10-21): every line prints at 80% of its size or more, for every reason together (`LAYOUT.floor`): the fitting's shrink and the piece's zoom for its pages multiply, so a piece is set smaller for its pages only as far as what its lines already lost allows (`data-fit` on the piece). A piece with room to spare grows instead (`LAYOUT.grow`): when every line fits unwrapped with room (`data-grow`, from `fit.js`), it is set at the largest step of a fixed scale, 14, 16, 18 or 20pt for aartis and ashtaks and 15, 16 or 17pt for Vedic texts (`pvved`), that takes no more pages than at its own size; English grows to 0.85 of those steps (`SCRIPTS.latn.steps`). The growth is a zoom on the piece, like the shrink. Chrome's check in page-sized columns sends a piece the browser lays out on more pages than planned back a step (or a little smaller, within the floor). Prose keeps a fifth of its last page spare when it grows, and in Safari prose does not grow (its plan is the one checked against Satish's PDFs).
- **Two columns and centring** (version 1.20.7, Satish 2026-10-21): in one language, an aarti or ashtak (not prose, not a Vedic text) prints as a block centred on the page with its lines left-aligned (`fit-content` on `.pvs`). One too long for one page in one column goes into two columns (`pack2` in `print.js`), down the left column, then the right, a stanza never split between them, the last page balanced, with a thin rule between (`LAYOUT.cols.gap`, 10mm). Only when every line fits half the width at that size (`data-half`, from `fit.js`), so two columns never wrap a line. Paginate tries the size steps, then its own size, then smaller down to the floor, and takes the largest that fits one page; it takes two columns only when that is larger than one column on one page (a tie stays in one column). If no size fits one page in either, it runs on in two columns at its own size when its lines allow, else in one column. `twoCols()` builds the pages as `.pv2p` rows of two `.pv2c` columns (`out.c` in the plan).
- **Best for each text** (version 1.20.9, Satish 2026-10-21, SIZES.md): the printout's default font (`P.pfn` empty or `best`; the pop-up's first choice, before the four text fonts). While printing, `data-font="best"` sets `--tf` to Classic (`SC Classic`, and `SC Kn Classic` for Kannada letters), and a Vedic text's original (`.pvved`) in Tiro Devanagari Sanskrit, the font that draws its svara marks. `fit.js` sizes it as Classic. An aarti's or ashtak's lines, the dhrupad at the top (`.pvref`, its bar hanging to the left) and the "↻ ध्रुपद" notes (`.rmk`) print left-aligned inside the centred block (on screen each line is centred).
- **New languages:** the fitting works out each column's script from its letters (`scriptOf` in `profiles.js`: Devanagari, Bengali, Gurmukhi, Gujarati, Odia, Tamil, Telugu, Kannada, Malayalam or Latin), so a new script needs nothing in the print code. Give it an entry in `SCRIPTS` only if `npm run print:audit` shows it looks larger or smaller than the others. The printed cells carry the page's own `lang`, and the Print pop-up's sample takes its first words from the page, so a new language needs nothing there either.
- **Page planning:** the view measures every unbroken block (stanza, verse group) in a frame the size of the printed page, then packs the blocks onto pages and forces a page break before each block that starts one. That is how no block is split across pages and the contents page gets real page numbers. The plan is then checked by laying the view out as a row of page-sized columns, which Chrome breaks the way it breaks pages: a block that lands on another page there gets its own break. A paragraph of prose never gets a forced break: it runs on from the page before, and a prose piece that spills up to 45% of a page onto a further page, or only just fills one, is set slightly smaller so it ends well inside a page and the contents numbers after it hold. A block taller than a page even at the smallest size (possible on a sideways page) may break between its lines, and starts below the block before it when a quarter of the page is still free, rather than on a page of its own.
- **The pop-up:** three rows. Dhrupad: Once or Every verse, for the printout only (`P.pref`). Page: for one language, Portrait or Landscape, shown pressed as last chosen (`P.por` "up" or "land"), or until then `CHOICE` in `js/print/profiles.js` (from the print audit): Portrait; for both languages it just says Landscape, side by side. Print font, with the first words of the first verse in each printed language. Then Cancel or Print (which takes the focus). Printing from the browser's own menu prints the same: one language in a column, both side by side (`dm()`).
- **Portrait or Landscape:** everything above works from the sheet as turned for the printout (`sheet(mode)` in `print.js`), and `@page { size: landscape }`, set as each printout is made, tells Chrome, Edge and Firefox. Safari keeps the sheet picked in its own dialog, so when Landscape is chosen the pop-up tells Safari readers to pick it there too. Released 2026-10-17 (`FEAT_SW` in `js/core/features.js`; set it to false to hide Landscape again, and every printout is then upright).
- **Printing on an iPhone:** Safari opens the print dialog only in answer to a tap. The printout for the layout last chosen is laid out ahead (`warm()`), so Print can print at once; otherwise the pop-up asks for one more tap (Print now). Printing never steps back in history (`ovDrop()`). The Home Screen app cannot print at all (checked on Satish's iPhone), so tapping Print there goes straight to Open in Safari, with the print choices in the address (read by `js/render.js`).
- **Slow phones:** the fitting and planning wait for the fonts for at most 2.5 s, then run with the fonts there are, so a slow phone still prints fitted text with page numbers.
- **Paper size:** Letter in the US, Canada, Mexico and the Philippines, A4 elsewhere (`LTR`).
- **Safari and every iPhone or iPad browser** (class `wk` on `<html>`) keep the page plan worked out from the heights; the check in page-sized columns is Chrome's. In Satish's Safari PDFs a printed page held up to a tenth less than that plan, so Safari's pages are packed to 90% (Chrome's to 96%), and prose that spills up to 45% of a page onto a further page is set at the largest size that takes a page fewer. Safari prints no page border or page-number footer: a fixed box is drawn once down the whole printout there, not once per page (Satish's Safari PDFs showed a box open at the bottom), so the border is Chrome's only; Safari's own headers and footers come from its print dialog. On a Mac, the print pop-up suggests Chrome, which turns the page itself and prints the border and page numbers.
- **Print font:** the pop-up's font picker sets `P.pfn`, the printout's font only (empty: the text font). The page takes it as `data-font` just while it prints (`pon()`/`poff()` in `print.js`), and the hidden copy the plan is measured in gets it too. Print dhrupad: `P.pref` (empty: as the page shows it) works the same way, through `data-ref`. Both are remembered for the next printout.
- **Safari on a Mac** prints about 16/15 larger than Chrome, and the page plan allows for that.
- **Tests:** `tests/print-items.spec.mjs` prints every text on its own in each layout and checks where every block and every line landed, and its size; `tests/print.spec.mjs` prints the whole Library in each layout and checks the contents page. `npm run print:audit` prints every combination a reader can choose (208 PDFs), into `tests/pdfs/`, with a report of anything that came out badly (see `tests/README.md`).

## Offline use and updates

- `sw.js` keeps the page, every file in `js/parts.js` (styles, scripts, texts, the main fonts and the three time-of-day pictures with the icons) in a cache named after the version (`aarti-v1.13`).
  - The page and its parts are always fetched fresh when possible, with a 3 s limit before the saved copy is used, so the page never mixes old and new parts.
  - Everything else comes from the saved copy and is refreshed in the background.
  - If the saved copy cannot be read within 2 s, the request goes to the network. Safari's storage can stall, and a Mac once sat on a blank page because of it.
- **The version is written twice on purpose:** in `sw.js` (`V`) and in `<meta name="version">` in `index.html`.
  - Browsers install a new service worker when `sw.js` itself changes. Not every browser re-checks the files it imports, so the version must sit in `sw.js`.
  - The page needs the version at start-up too.
  - `tests/offline.spec.mjs` fails if the two differ.
- **`_headers`** lets phones keep font files for a year and pictures for a week without asking again. The page, styles and scripts are always re-checked (`no-cache`), so an update reaches readers on their next visit.

## Oldest supported browsers, and the fallbacks they need

The floor is **iOS 15.4** (iPhone 6s / 7, iPad Air 2 / mini 4 run up to iOS 15.8). The list is in `tests/.browserslistrc`. `npm run lint` fails on any CSS or JavaScript feature those browsers lack, unless the code checks for it first.

| Fallback | Why |
|---|---|
| `css/99-fallbacks.css` | `color-mix()` needs iOS 16.2. Without these plain colours, buttons and cards on iOS 15 lose their colours. The file must stay last. |
| `vh` before `dvh` / `svh` | Older Safari has no dynamic viewport units. |
| `setTimeout` when there is no `requestIdleCallback` | Safari has no `requestIdleCallback`, so the print warm-up just waits a moment. |
| Class `wk` on `<html>` | WebKit's print layout (see Printing). |
| `meta[name="version"]` read with a default | The page still runs if the tag is missing. |
| 1.5 s reveal | The page shows even if the site script fails to start. It also works when the phone asks for reduced motion, which turns off every other animation. |

## Things tried and rejected

- **`content-visibility: auto`** on the pieces, to skip laying out pieces off screen. It changes how margins collapse, which moved pieces 10–22px, and text inside skipped content reads back empty.
- **Reordering the CSS by topic.** The cascade depends on the order rules were added, and moving rules caused about 12,000 conflicts. The CSS was split where it stood instead.
- **An SVG sprite for repeated icons.** The page has 41 icons, of which 28 are different. Compression already makes the repeats almost free, and `<use>` inside buttons behaves differently in older Safari.
- **Moving the version into `js/parts.js` only.** See *Offline use and updates*.

## Checking a change

- `cd tests && npm run lint && npm run types && npm run unit && npm test` runs the checks on a computer.
- GitHub runs every browser on each pull request.
- `tests/README.md` says what each suite protects and how to refresh screenshots.
- `tests/MANUAL.md` is the short checklist for real phones and screen readers.
